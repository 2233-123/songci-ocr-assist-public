# 宋词择律 OCR 提示器

玩宋词择律类玩法时，游戏会给你一句词，让你在几个词牌里选出正确的那个。
这个 App **在屏幕上把正确答案框出来** —— 不用查资料，看一眼框就知道选哪个。

它只做三件事：**看屏幕 → 查词牌 → 画框**（另外顺带告诉你这句词会给什么效果）。
不修改游戏、不注入进程、不代替你操作。

> ⚠️ **请注意**：这是第三方工具，与游戏官方**无任何关系，也未获其授权**。
> 使用辅助工具可能违反游戏用户协议并带来**账号风险**，请自行判断、风险自负。

## 怎么用

### 1. 安装

到 [Releases](../../releases) 下载最新的 `songci-assist-vX.Y.Z-release.apk` 安装。
首次安装需要在系统设置里允许「安装未知来源应用」。

- 需要 **Android 8.0 及以上**
- 包体约 40 MB，绝大部分是**随包的中文识别模型** —— 好处是**完全离线**，不依赖网络

> 升级**可以直接覆盖安装**（签名一致，不会丢设置）。当前最新版本见
> [Releases](../../releases)，各版修了什么见「[更新记录](#更新记录)」。

### 2. 授权

打开 App，引导页会逐项检查权限。**其中第 5 项最容易被忽略，但它是必需的**：

| # | 权限 | 为什么需要 |
|---|---|---|
| 1 | **悬浮窗** | 在游戏画面上显示高亮框 |
| 2 | **通知**（Android 13+） | 取帧服务需要常驻通知（通知里带「停止」按钮） |
| 3 | **屏幕录制** | 取帧的前提，由前台服务持有、整局有效 |
| 4 | **忽略电池优化**（建议） | 否则长时间在后台可能被系统掐断；小米/华为/OPPO 还需在「自启动/后台白名单」里放行 |
| 5 | **修改系统设置** | **必需**。Android 16 在屏幕方向变化时会直接停掉录屏；游戏横屏、桌面竖屏，切一次窗口投屏就废了。授权后 App 在录制期间自动锁横屏，停止时恢复原设置 |

> 屏幕录制 Android 要求**每次使用都重新授权**，这是系统限制，不是 App 的问题。

### 3. 开始提示

1. 先在 App 里完成上面的授权
2. **切到游戏**，进入择律页面
3. **在游戏里点一下悬浮球**开始取帧
4. 首句出现后通常在**半秒内**正确的词牌上就会出现**高亮框**

> ⚠️ **不要从 App 里点「开始」再切回游戏** —— 切窗口会改变屏幕方向，
> Android 16 一旦方向变化就停掉投屏（表现是一直收不到帧）。
> 悬浮球就是为了让你**不用离开游戏**就能启动。

### 悬浮球与提示条怎么操作

**悬浮球**：

| 操作 | 效果 |
|---|---|
| 点一下 | 还没开始时：启动取帧（会弹录屏授权）<br>运行中：暂停 / 继续 |
| 拖动 | 移动位置（松手自动吸附到屏幕边缘，位置会记住） |
| 长按 | 退出 |

**顶部提示条**（显示「首句 → 词牌」和词句效果的那一条）：

- **可以拖到屏幕任意位置**，没有方向限制；大半拖出屏幕也行，会留下一条边方便拖回来
- **别让它盖住游戏的首句文字或选项气泡** —— 那些字会被 App 自己一起读进去，影响识别。
  拖到不挡字的地方即可（事件日志里也会对这种情况给提示）

> 没匹配到词句时，提示条会变成一条**淡色的 `···` 占位条**（不是消失）——
> 这样你随时都能抓住它，而不是等它出现了才能拖。

## 使用说明与排查

**框出来的位置不对 / 没有框？**

- 游戏的艺术字体偶尔会被 OCR 认错。认错 1 个字时 App 会自动纠正，
  错得更多时**宁可不画框，也不会画错** —— 画错比不画更糟，所以这是有意的选择
- 首句还没显示完（画面还在渐入）时识别不出来，等一秒再看

**一直不出框？**

- 确认已经**点过悬浮球**（球是实心的才在运行）
- 确认录屏授权选的是「整个屏幕」而不是某个应用窗口
- 有些系统的电池优化会杀掉后台服务，建议在系统设置里给 App 关闭电池优化 / 加入白名单

**会不会很费电 / 发热？**

- 需要持续录制屏幕并识别文字，会比待机耗电，建议需要时再开
- **可以在「性能」设置里把取帧频率调低**（见下节），1~4 fps 足够用且明显更省电

**性能设置（想更省电或更快，都可调）**

App 首页有「性能」区块：

| 设置 | 说明 |
|---|---|
| **取帧频率** | 1 / 2 / 4 / 8 / 15 fps / 不限速。越高出框越快，耗电发热也越高。默认 8 fps |
| **命中正确选项后暂停密集取帧** | 认出并框住正确选项后放慢取帧等你作答；你一在屏幕上点击就立刻恢复。最迟几秒后自动恢复（防止游戏自己换题时卡住）。**如果觉得出框变慢，把它关掉即可** —— 它只在省电上有收益 |

「不限速」**不会真的每帧都读** —— 识别本身要 100~300 毫秒，那是物理上限。
改完**立刻生效**，不需要重开投屏。

**隐私**

- App **不联网、不采集、不上传任何数据**，识别全部在手机本地完成，没有服务器
- 唯一的对外通信来自 Google ML Kit SDK 自身（发送 API 性能/使用指标，
  **不含你的屏幕画面与识别结果**）

## 它是怎么工作的

1. **录屏取帧** —— 通过系统的 MediaProjection 接口读取屏幕画面（1:1 原始分辨率）
2. **文字识别** —— Google ML Kit 中文离线模型在本地识别画面文字
3. **两段式匹配**
   - 在画面上部找到**首句**，用编辑距离相似度去索引里查最接近的词
   - 查到的词带来一个**词牌名**，再在画面中部找到写着这个名字的选项气泡
4. **画框** —— 用悬浮窗在那个气泡上画一个高亮框
5. **报效果** —— 认出首句的同时，在顶部提示条里追加**这首词会给哪些效果**

索引里有 **99 条词句 / 40 个词牌**，随包提供、离线查表。

### 词句效果怎么显示

认出首句后，顶部提示条**单行**显示结论与效果，中间用 ` ｜ ` 分隔：

```
应选：贺新郎（屏上没找到选项气泡） ｜ 军心+4、战斗力+2
```

- **只认到首句就显示**，不必等找到气泡（词牌定了，效果就定了）
- 显示形式是**名称 + 数值**；负数是减少，例如 `腐化-4` 表示降低腐化（是好事）
- **不显示「词元」**（加词元的效果一律不报）
- 效果挂在**整条词句**上（游戏数据本身不按句拆分），所以「这句的效果」= 这首词的效果

> 为什么是单行不是两行：曾经做成两行，结果提示条底边压到游戏首句文字上（首句固定在屏幕
> y≈0.19 处，是取帧时一起被识别的），导致**识别不出新句子**。所以内容只能加在横向上。

数值来源：游戏配置的 `EffectTypeList`（效果种类）+ `EffectParamList`（数值）。

### 匹配的准确度（可复算）

对索引里每条词句随机注入整字替换后测试（阈值 `0.65`）：

| 注入错字数 | 画错词牌（误报） | 能给出提示 |
|---|---|---|
| 0 | 0 | 100% |
| 1 个字 | **0** | 100.00% |
| 2 个字 | **0** | 98.99% |
| 3 个字 | **0** | 96.97% |

**任何错字量下都没有出现过"画框但画错"** —— 这是本项目的首要原则。
复算：`python tools/tune_matcher.py`

**本仓库不含任何游戏数据。** 游戏导出的原始配置属于游戏素材，需要的话请自行从自己的设备导出

只有「词句首句 → 词牌名 → 词人」这样的事实性对应（约 20 KB），是 App 离线查表所必需；
词句本身属**公有领域**（作者均为唐宋人）。仓库不含任何游戏素材（图片、音频、字体、原始配置）。

### 构建

```bash
# 需要 JDK 17 + Android SDK（platform 34 + build-tools 34.0.0）
./gradlew assembleDebug          # 打 debug 包
./gradlew assembleRelease        # 打 release 包（配了 keystore.properties 才签名）
./gradlew testDebugUnitTest      # JVM 单测，无需设备

python tools/verify_all.py       # 一键自检：索引校验 + 匹配复算 + CI/版本一致性
```

> 本仓库不含 `assets/effects.json`，依赖它的 10 个单测会自动跳过（`Assume`），
> 所以本仓库跑出来的数字是 **178 个用例中 168 个通过、10 个跳过**。

`app/src/main/assets/verses.json`（词句索引）已随仓库提交，**克隆下来即可直接构建**，
不需要任何数据准备。

只有**重新生成索引**才需要自备游戏数据：把游戏导出的两个 JSON 放进 `data/`
（结构与字段见 [data/README.md](data/README.md)），然后跑 `python tools/gen_verse_index.py`。

> **`assets/effects.json`（词句效果表）本仓库不分发** —— 它由 `tools/gen_effect_index.py`
> 从游戏数据生成，内容与 `verses.json` 同性质（首句文本）。所以：
> - 缺它**不影响构建与出框**（效果只是可选增强，App 端加载失败只记一行日志）
> - 依赖它的单测会自动**跳过**（`Assume`），`verify_all.py` 也会跳过该项校验
> - 想要这个功能，自备游戏数据后跑 `python tools/gen_effect_index.py` 即可

> ⚠️ **本工程最初在含中文的目录下开发**（Windows 上的 `E:\Desktop\宋词辅助`）。
> AGP 默认会对非 ASCII 路径直接报错，工程里用 `android.overridePathCheck=true` 关掉了该检查。
> 若遇到离奇失败，优先怀疑这一项；想避开就把仓库克隆到纯 ASCII 路径。

### 目录结构

**先看三层隔离**（Gradle 源集，目录即边界）：

| 目录 | 是什么 | 会不会进 APK |
|---|---|---|
| `app/src/main/` | **生产代码**（22 个 Kotlin 文件，约 7100 行） | ✅ 会 |
| `app/src/test/` | **JVM 单测**（31 个文件，约 4100 行）：断言测试 + 诊断探针 + 测试基础设施 | ❌ 不会（`testImplementation` 依赖也隔离） |
| `tools/`、`data/`、`docs/` | **开发期工具与文档**（Python / 数据说明 / 设计文档） | ❌ 不会 |

> 实测确认：发布包里**不含任何测试类**（`MatcherTest` / `TestStats` / `LiveFrameProbe` … 全部不在 dex 中）。


### 匹配算法

- 匹配键 = **首句**（正文到第一个断句符）去掉全部标点与空白
- 相似度 `sim(a,b) = 1 − Levenshtein(a,b) / max(len(a), len(b))`，阈值 `Config.SIMILARITY_THRESHOLD = 0.65`
  （该式在 Python 侧与 Kotlin 侧**必须一致**，改一处要同步改另一处）
- 两段式：顶部 `y∈[0, 0.45H]` 找首句 → 命中后中部 `y∈[0.30H, 0.80H]` 找文本等于词牌的块
- 首句被 OCR 拆行时按 Y 相邻拼接（最多 2 行）；同一行被拆成左右两段时按 X 拼接。
  两条防回归规则见 `Matcher.sameLine` / `Matcher.mergeAdjacent` 的注释：
  **同排归并要求 X 基本不相交**（避免把同排的 UI 标签并进句子），
  **上下拼接排除"一方被另一方横向包住"**（避免小标签粘进首句把相似度顶到阈值以下）
- **首句取舍：位置优先**（0.9.7 起）。换题瞬间上一题首句会残留在上方，而两组相似度
  常常都是满分 —— 分数无法区分，只能靠位置（更靠下 = 当前题）。
  顺序为 **位置 > 相似度 > 行数**。
- 词牌气泡先精确匹配，失败时允许**同长度**的模糊匹配，且要求是**唯一最优**
- **形近字等价**（0.9.9 起用于气泡，**0.10.1 起也用于首句**）：字面模糊匹配按编辑距离算，
  3 字词牌错 1 字只有 `0.667`，而阈值是 `0.66` —— **只高 0.007**，所以**错 2 字必然失败**。
  实测游戏字体下：`丑奴儿`→`卫奴儿`/`卫奴几`、`鹧鸪天`→`鹤鸽天`、
  首句 `甚矣吾衰矣`→`甚美吾衰吴`。修法是**逐位形近等价比较**

  ```kotlin
  // 逐位比较，同组即算相同 —— 不同位置各自混淆也能正确表达
  confusableEquals(a[i], b[i])
  ```

  > 曾用「把形近字全局折成占位符」的写法，**是错的**：把 `几` 与 `丑` 放同组时，
  > `卫奴几`→`②奴②`、`丑奴儿`→`②奴儿`，反而认不出来。
  > 因为 `卫` 混的是**首字**、`几` 混的是**末字** —— 全局映射表达不了位置关系。
  >
  > 安全性由全量两两断言守护：40 个词牌任意两个、**99 条首句任意两条**，
  > 形近相似度都不到阈值。

- **首句越短越怕错字**（结构性弱点，值得知道）：

  | 首句长度 | 最多容忍错字 | 再多错 1 个时 |
  |---|---|---|
  | 5 字 | 1 个 | 0.600 ❌ |
  | 6 字 | 2 个 | 0.500 ❌ |
  | 8 字 | 2 个 | 0.625 ❌ |
  | 12 字 | 4 个 | 0.583 ❌ |

  索引里 5~6 字的短首句只有 3 条（`燎沉香消溽暑` / `甚矣吾衰矣` / `老去凭谁说`），
  全是高风险条目 —— 所以短首句的错字**只能靠形近等价兜住，指望阈值不够**。

### OCR 速度的实际约束（勿再走弯路）

实测结论，写下来避免重复踩。**这里有过一次严重的误判，先说明**：

> 早期版本在代码注释与本 README 里都写着「全屏单次 OCR 要 1.6~2.4 秒」。
> 那个数字是**从日志时间戳错误推断**出来的（把"帧处理间隔"当成了"OCR 耗时"），
> 一直没人验证，导致后续一系列优化判断都建立在错误前提上。
> **真机实测（独立基准 App，29 帧语料）单帧中位只有 113ms，最快 69ms。**

修正后的数据：

| 项目 | 实测 |
|---|---|
| ML Kit 中文 bundled，单帧（2608x1200 裁到 0.85） | **中位 141~218ms** |
| 冷启动 | 18~24ms |
| ML Kit 每次调用的**固定开销** | **约 150ms**（读 1/4 像素并不更快） |

由此得到的结论：

- **每次调用有约 150ms 固定开销，与像素数关系不大。** 所以「多调一次只读一小块（补救）」
  是亏的：实测补救成功率仅 **2/95**，却让每帧多花 235ms → **已在 0.9.0 彻底移除**。
  正确做法是**只调一次但读满**。
- 「等画面停稳再 OCR」**走不通**：游戏顶部有持续飘动的粒子动画，画面永不静止
- 「二次识别放大 2 倍」**无收益**：基准实测 1× 与 2× 气泡命中数完全相同（26/28），
  2× 却贵 45% —— ML Kit 内部本就会归一化，双线性插值反而模糊手书笔画
- 「缩放整帧」**不可行**：实测首句字高 38px、**气泡字高仅 18px**，缩到 85% 只剩 15px，
  手书字体会直接读不出
- 「换 OCR 引擎」收益存在但需实测：桌面基准里 PP-OCRv5 达 97%（ML Kit 约 79%），
  但端侧移植尚未完成

**目前有效的优化**：取帧档位做成用户可调（默认 8 fps，上限由单帧成本决定，实测约 4.9 fps）、
首遍裁掉底部 15% 像素、以及下面那些"消除无效等待"的修复。

### 取帧侧的修复

曾长期卡在"投屏建立后立刻被系统回收"，最终定位如下（细节见 `ScreenFrameReader` 类注释）：

| 现象 | 根因 | 修法 |
|---|---|---|
| 投屏 21ms 就被回收 | 尺寸变化时 release 了 VirtualDisplay（官方文档明确警告过） | 只换消费者，绝不 release |
| 换消费者后只续 2 帧 | `setSurface(新)` 后立刻 close 旧 reader → BufferQueue 被弃用 | 先 detach → resize → attach → 延后回收 |
| 画面黑底 + 角落一块灰 | 用了 `maximumWindowMetrics`，与真实显示尺寸不一致 | 改用 `Display.getRealMetrics()` |
| **闪退** `IllegalStateException: buffer is inaccessible` | `toPixels` 用了 `buffer.asIntBuffer()`，其视图在源 buffer 失效后仍被读；且异常在 ImageReader 的 Handler 线程逃逸 | 不用 int 视图、接住所有 Throwable 丢帧；`Handler.Callback` 逐条兜底 |

### 悬浮窗侧的修复

| 现象 | 根因 | 修法 |
|---|---|---|
| 部分华为/鸿蒙设备上**游戏按钮点不动** | 高亮层是 `MATCH_PARENT` 全屏窗口，触发 OEM 的触摸遮挡判定 | ① 保留 `FLAG_NOT_TOUCHABLE`；② 曾改为"按内容定尺寸的窄窗口"绕开 —— 但这引出了下面两条，**0.9.5 起改回恒定整屏 + 依赖 flag** |
| 顶部「应选：X」会**上下漂移** | 状态条与高亮框**共用一个窗口**，窗口位置是两者包围盒的**并集** | 状态条**独立成固定窗口**（0.11.8 起还可自由拖动），见 `StatusBarView` |
| **框从左上角"飞"过来** | 窄窗口的 `params.x/y/width/height` 每帧都变，`WindowManager` 默认播放窗口移动动画 | 窗口**恒定整屏、位置钉死 (0,0)**，只改画布内容 |
| **框只画在左上角** | 两处叠加：① `layoutFor` 残留的 `contentOriginY=-444`（那是窄窗口时代的公式）；② 窗口用了 `resources.displayMetrics`（应用窗口 2464x1152）而非 `getRealMetrics`（真实显示 2608x1200） | 强制 `contentOrigin=(0,0)`；窗口与绘制都用 `getRealMetrics` |
| **框画在自己的提示框上、且永不消失** | 状态条文案「应选：X（屏上没找到选项气泡）」含词牌名，OCR 断块后产出**恰好等于词牌的块**，被 `scanOptions` 当成气泡；形成自锁：框在状态条上 → 文字被读回 → 继续命中 → TTL 不断重置 | 新增 `FramePipeline.selfDrawnBounds`，**排除 App 自绘区域**（用实际几何，不猜阈值） |

> 原则：**屏幕上不出现大面积覆盖窗口**曾是本项目的取舍，但那让窗口几何频繁变化，
> 引出了动画与坐标两个 bug。现在的做法是**窗口恒定整屏 + `FLAG_NOT_TOUCHABLE`**：
> 触摸穿透由 flag 保证，窗口本身不动，绘制内容随帧更新。

### 分发

GitHub Actions 产出 `app-debug.apk` 与 **`app-release.apk`（已签名，分发用）**。
CI 里 4 个 Secrets 配好后自动签名（`KEYSTORE_BASE64` / `KEYSTORE_PASSWORD` / `KEY_ALIAS` / `KEY_PASSWORD`）。

发布包自检：

```bash
python tools/check_apk.py verify app-release.apk   # 签名 + 包名/版本/权限/ABI/assets/模型
python tools/check_apk.py certs  app-release.apk   # 只看证书指纹
```

> 本工程**不做第三方加固**（如 360 加固保）。加固会改写 DEX、hook 反射与 Binder，
> 而本 App 的关键能力（MediaProjection 录屏、`TYPE_APPLICATION_OVERLAY` 悬浮窗、
> ML Kit 的 native OCR 管道）恰好都依赖这些机制，加固后需逐项真机复测，
> 收益（提高逆向门槛）与风险（录屏/悬浮窗/OCR 失效）不成正比。
